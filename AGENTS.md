# AGENTS.md

## Filing an issue (for AI agents and humans)

Open issues through the [issue forms](https://github.com/mnaoumov/obsidian-custom-attachment-location/issues/new/choose), not as blank issues.

Filing from the CLI or the API (`gh issue create --body`, or an AI agent filing for you) skips the form, and `gh issue create --template` cannot load an issue form. In that case, open the matching form in [`.github/ISSUE_TEMPLATE/`](https://github.com/mnaoumov/obsidian-custom-attachment-location/tree/HEAD/.github/ISSUE_TEMPLATE), copy every field as a `### <label>` heading in the form's order, and fill in each one. Always state the plugin version, the Obsidian version and your operating system.

## Sidecar names belong to the base, and imports have a batch lifetime

`src/sidecars/sidecar-attachments-component.ts` keeps the `ImportedAttachment.data` buffers in a batch until the editor or app import finishes. A sidecar saves its base first through the same saver, and memoizes that save, so reversed order and nested import sinks still generate one base name. Match the full base name first (`document.html.p7s`), then a unique non-sidecar stem (`video.srt` beside `video.mkv`). `sidecarExtensions` accepts case-insensitive extensions with an optional dot; file names match exactly. An empty list is a real value meaning "pair nothing": its binding turns off the library's empty-means-default reset and the default placeholder, and the row's reset button is the way back to the defaults. Paired imports preserve bytes so JPEG conversion cannot invalidate a signature. A later standalone signature uses the original-name store only when it identifies one base in the current note's resolved destination folder; ambiguous or absent bases keep their names and report a notice.

The component intercepts `vault.rename` and awaits companion moves, including unlinked companions and chained signatures. It refuses occupied companion destinations before moving the base and rolls back earlier moves on failure. Collect's proper-path resolver skips independent sidecar moves. The `RenameNote` resolver likewise returns a sidecar's current path: the dependency may plan linked files before or after the base, and only the base's eventual move owns the companion destination. New import and API read contexts retain their own semantics.

`src/sidecars/sidecar-group.ts` applies the same matcher to existing folder-local groups. Unused deletion filters its final candidate set so a group survives when any member survives, including references found only in canvas JSON or note text. Ambiguous and orphan sidecars remain independent. Collect Copy and Move-to-proper-folder copies carry unlinked descendants and chained signatures using the base's actual collision-suffixed destination. An identical reused base can reuse byte-identical companions; conflicting companions refuse the copy, and incomplete copies roll back only files created by that operation. Move-to-proper-folder then retires the original base together with the companions it copied (`getSidecarDescendantPaths`, snapshotted before the copy), and only when none of them is still linked; a companion still linked keeps the whole original group. An ancestor base of a moved signature was never copied, so it is never deleted.

The mobile share sheet names files before core saves them, one by one, through `vault.getAvailablePathForAttachments` and `createBinary`, so `src/attachment-location/share-receiver-import-files-patch-component.ts` pairs them itself with the component's `findBase`. It generates only bases, derives every companion (chains included) from its base's name, keeps and reports orphan or ambiguous sidecars, and leaves the input order alone. Core would suffix a taken base alone (`doc 1.html` beside `doc.html.p7s`), so in a batch with any sidecar every root first probes its destination folder and claims the first `duplicateNameSeparator` suffix free for its whole group, in the vault and among the batch's earlier roots. A batch without sidecars keeps core's own collision handling. A shared `.md` file (core lowercases the extension) is left out of all of this: core saves it as a note through `vault.getAvailablePath`, which never strips the `__IMPORT_FILES__` prefix, so it keeps core's name and location.

The real editor drop test waits for the clipboard interception as well as the editor element. `LayoutReadyComponent` waits for ancestry loading, so a visible editor alone can precede patch installation in a fresh harness vault; dropping during that interval exercises core's original import instead of the feature. Detect the patch by its monkey-around wrapper (its prototype is a function other than `Function.prototype`), never by the method's name: Obsidian's own `insertFiles` is anonymous, so a name check passes before anything is patched. Nor by `prototype !== Function.prototype` alone: in Obsidian 1.15.0 `insertFiles` is `async`, its prototype is `AsyncFunction.prototype`, and that check passes before anything is patched too. A note opened by the test raises its `active-leaf-change` on a debounce, so the patch can arrive after a drop made straight away. The patch itself is installed from the first loaded markdown view, retried on `active-leaf-change`, `layout-change` and `file-open`; the last is the one that catches a note opened into the tab that is already active.

## Inserted link text is prepared before synchronous link generation

Obsidian's `generateMarkdownLink` returns a string, while a token may be asynchronous. `AttachmentPathManager` evaluates `insertedLinkText` while resolving an import destination and keeps at most 100 results for one minute, keyed by attachment and source note and checked against the current template. The link patch consumes the prepared value even when an explicit alias wins, so it cannot leak into a later link. For an existing attachment with no import in flight, a template made only of the name and extension tokens is filled synchronously, using the same parser, string schema and formatter as those tokens: `{{attachmentFileName}}`/`{{attachmentFileExtension}}` read the file, and the `original` forms read the persistent original-name store, which is consulted (and a missing record reported) only when one of them appears. Other templates apply during imports only. During an import the preparation passes the saved name as `attachmentFileName`, so both paths agree that it is the attachment's name when its link is written. `{{attachmentFileName}}` is what the old `shouldSetLinkDisplayTextToAttachmentFileName` toggle migrates into (`LegacySettingsConverter`, only when the template is blank); there is no separate toggle any more, so a link-text need is a template, never a new switch. Images skip this template because numeric aliases change embed size; explicit aliases and cached sizes take priority. Link delimiters are converted to full width equivalents so a name cannot become part of the target or terminate the link.

The Android arm of `inserted-link-text.cross-platform.integration.test.ts` imports a PDF through the real share receiver using a blob URI, then generates its link from the saved file. `shareReceiver.importFiles` saves the file without inserting an editor link; waiting for note text immediately after that call tests an insertion it does not promise. The test covers the receiver's pre-save renaming and original-name lookup, while an OS share intent remains outside the Appium fixture.

## Advanced Rename and Delete Handler is a declared dependency, so every test vault carries it

`src/plugin.ts` declares `Advanced Rename and Delete Handler` through `getPluginDependencies()`. Until its API is published at contract `^1.1.0` by version `3.0.1` or later (`minPluginVersion`: 2.1.x publishes the same contract but reads the attachment-unit-folder designation off the graft 15.0.0 removed, and up to 3.0.0 it is built on an `@mnaoumov/obsidian-lib` older than 6, which publishes into `globalThis.__obsidianDevUtils`, a registry lib 6 never reads), this plugin's `onloadImpl` does not run: no commands, no patches, no settings tab of its own — the library shows a blocked tab and a notice that install it in one click.

Consequences for anyone touching the tests:

- **Every integration vault seeds it.** `scripts/helpers/advanced-rename-and-delete-handler-seed.ts` downloads the pinned RELEASE (cached under `.cache/`) and writes it into the vault with a `data.json` that leaves renames, attachment-folder moves and deletions off, and sets the read-back values to this plugin's historic defaults (`DeleteWithEmptyParents` and so on). The desktop and Android projects get it from `scripts/vitest-global-setup.ts`, wired in `scripts/vitest-config.ts`; the demo-vault and performance projects compose it into their own setups. A new project that opens a vault needs the same, or every suite in it meets this plugin blocked.
- **No suite may disable or remove it.** It outlives each file, and taking it away closes this plugin's gate for every later file in the run. A suite that needs its settings changed proposes them through its `migrateSettings` API and hands the previous values back — see `src/attachment-unit-folders/attachment-unit-folder-rescue-cross-plugin.desktop.integration.test.ts`. The store-screenshot captures are the one exception: each owns its vault outright, runs alone in its project and needs renames on from the first frame, so it writes the handler's `data.json` itself, from the seed's exported `ADVANCED_RENAME_AND_DELETE_HANDLER_SEEDED_SETTINGS`.
- **Find its dialogs by TITLE, never with a bare `.modal-container` lookup.** `migrateSettings` opens a dialog on the way in *and* on the way out, and the behavior under test may have its own dialog open at the same time — anything that fails while the handler is asking something leaves two boxes on screen. A bare `document.querySelector('.modal-container')` then takes whichever is first in the DOM, and the teardown's throw (`the handler's settings dialog has no OK button`) **replaces the assertion that actually failed**, so the run reports the wrong defect entirely. `src/shared-attachments/shared-attachment-tie-cross-plugin.desktop.integration.test.ts` matches on the `.modal-title` prefix for exactly this reason.
- **Unit tests publish a stand-in API.** `src/plugin.test.ts` publishes an empty API for the dependency in `beforeEach`; without it the gate never opens and nothing past the base loads. `unpublishProviderApi()` withdraws it, which is how the blocked path and the surface teardown are tested.
- **Its contracts are the provider's own, copied.** `src/advanced-rename-and-delete-handler/api/` holds that plugin's root `api.d.ts` and `api-contract.ts` VERBATIM, with its `api-contract.test.ts` beside them (import paths adjusted). The migration and read-back contracts in `src/advanced-rename-and-delete-handler/advanced-rename-and-delete-handler.ts` take their entries from it, schemas included. Refresh the copy from the provider's repository rather than editing it.
- **`onloadImpl` runs again each time the gate reopens.** Anything it stores outside its children has to be reset when the surface unloads — `attachmentCollector` and `pluginApi` both are, because `collectAttachmentsInAbstractFiles` and the published API are reachable from outside and would otherwise drive torn-down components.

## A command gate belongs on `canExecuteAbstractFile`; `canExecuteAbstractFiles` answers one surface out of three

`AbstractFileCommandHandler` exposes two overridable gates, and they are not interchangeable:

- `canExecuteAbstractFile(abstractFile)` is the per-file predicate. The **command palette** reaches it through `canExecute()` (`shouldAddToCommandPalette() && !!activeFile && this.canExecuteAbstractFile(activeFile)`), the **single-file menu** calls it directly, and the base's `canExecuteAbstractFiles` composes it over every entry.
- `canExecuteAbstractFiles(abstractFiles)` is reached by the **multi-select menu alone**.

So a handler that overrides only the second, leaving the first at its base `return true`, gates one surface out of three — and the other two offer a command that then walks its own filter and does nothing. All three of this repo's gated handlers were that shape, and it was caught only because `excalidraw-source-note-skip.desktop.integration.test.ts` asks `checkCallback(true)` — the same availability question Obsidian asks before listing a command. Every unit test passed while the palette was still offering it, because the unit tests called the override.

Two consequences for anyone adding or changing one:

- **Put the predicate on `canExecuteAbstractFile` and let the base compose it.** All three gated handlers are worked examples: `collect-attachments-in-file-command-handler.ts` (plain `isNote`, so a drawing is still collected from), `delete-unused-attachments-in-file-command-handler.ts` and `move-attachment-to-proper-folder-command-handler.ts` (both `isNoteEx`).
- **Do not open such an override with `super.canExecute()`.** The three handlers used to, and it tests the ACTIVE file — a condition with nothing to do with a menu built from the files the user clicked, and one that turns into a real false negative the moment `canExecuteAbstractFile` is implemented, hiding the multi-select item whenever an unrelated file is open.

## The published reads are non-interactive, and a new interactive token must say so

`src/plugin-api/plugin-api-impl.ts` answers a consumer's questions by driving the same `AttachmentPathManager` the commands drive, under `ActionContext.ReadApi`. That context exists for one reason: **a read has no user to ask.** A consumer auditing a whole vault calls `getAttachmentFolderPath` once per note, and a folder template holding `{{prompt}}` would raise one dialog per note.

- **A token that would open anything must gate on `isNonInteractiveActionContext`** (`src/tokens/token-evaluator-context.ts`), not on `ActionContext.ValidateTokens` by name. `prompt-token.ts` is the only such token today and is the worked example; naming the context directly is how the next one silently starts prompting an audit.
- **`migrateSettings` asks through its OWN dialog, never through a token.** It receives the collect settings `Consistent Attachments and Links` hands over, and the user approves them in `src/plugin-api/collect-settings-migration-modal.ts`. It never evaluates a template, so it gives `{{prompt}}` no way in. Keep it that way: the non-interactive rule above is about the READS.
- **`collectAttachments` is an ACTION and asks exactly what the `Collect attachments` commands ask** — it drives the same queued collector, under the command's own contexts, not `ReadApi`. Two things keep that honest: it resolves to nothing and never reaches the collector when no named path exists (an empty list is what the collector confirms with the user), and it awaits the collect through `addToQueueAndWait` so a consumer can sequence on it. The plugin instance's `collectAttachmentsInAbstractFiles` is its superseded predecessor (a JSDoc note, not `@deprecated`: the fleet config forbids disabling `no-deprecated`, and its own tests must keep calling it) and still delegates to the same collector.
- **`ActionContext.ReadApi` falls into every `default:` branch** in `attachment-path-manager.ts`, so a read answers about the NEW-attachment destination (`attachmentFolderPath`) and the ordinary generated file name. That is deliberate and is what `api.d.ts` promises. The collect destination (`collectedAttachmentFolderPath`) is a different question and is not published yet.

## `api.d.ts` and `api-contract.ts` at the repo root are the whole published surface

The convention: a consumer copies `api.d.ts`, which imports `obsidian` alone, or references it where it sits, with no build-time dependency on this repository. `src/plugin-api/plugin-api.ts` holds only the runtime half (`PLUGIN_API_CONTRACT`, `PLUGIN_API_VERSION`) and RE-EXPORTS the types from it, so each type is declared once. The contract itself is the root `api-contract.ts`, `CUSTOM_ATTACHMENT_LOCATION_API_CONTRACT`: an `input` and an `output` Standard Schema for every method. It imports only `obsidian`, `./api.d.ts`, `@mnaoumov/typescript-lib` (the contract types, the schema builders and the guard builders, in its `api-contract` and `type-guards` entry points) and `@mnaoumov/obsidian-lib` (the file guards, in its `file-system` entry point), so the file is this API's constant plus the guards for its own shapes, and a consumer copying it adds those two packages. It is typed `TypedApiContract<CustomAttachmentLocationApi>` from that package, which is NOT `@mnaoumov/obsidian-lib`. `PLUGIN_API_CONTRACT` is that constant assigned to `ApiContract`, which is what checks the schemas are ones the registry accepts. It is not `api.ts` because TypeScript would resolve `./api.d.ts` to that file's own declarations. Adding a member means editing `api.d.ts`, `api-contract.ts` (its mapped type refuses to compile without both schemas), the impl, and the version — a minor bump for an addition, which is what lets a consumer keep asking for `'^1'`.

## The `getAvailablePathForAttachments` patch grafts nothing

Until 15.0.0 the patch in `src/attachment-location/vault-get-available-path-for-attachments-patch-component.ts` grafted `extended` and `checkIsAttachmentUnitFolder` onto the method it patches. Both are now API members only (`getAvailablePathForAttachments`, `isAttachmentUnitFolder`, contract `1.3.0`), and the patch keeps nothing but Obsidian's own signature. Do not add a member back onto the patched method: a capability another plugin needs goes into `api.d.ts` and `api-contract.ts`.

`@mnaoumov/obsidian-lib` 3 reads the designation through the API: `findAttachmentUnitFolderPath({ app, ... })` asks this plugin's published `isAttachmentUnitFolder`, so this plugin's own collect, delete-unused and owner-resolving code reaches it through the registry. A unit test that needs a designation therefore publishes a stand-in API under this plugin's id (`publishAttachmentUnitFolderDesignation` in `src/delete-unused-attachments/unused-attachments-remover.test.ts` and `src/collect/attachment-collector.test.ts`). An integration test that drives the resolver reads the API off `window.__obsidianLib.pluginApiRegistry`, the way `src/plugin-api/programmatic-rename-note-path.desktop.integration.test.ts` does.

## An integration suite edits settings through `editAndSave`, never onto the settings object

The ordinary desktop suites run in both `integration-tests:desktop` and `integration-tests:desktop:after-layout-ready`. Their setup modules share `scripts/helpers/vitest-global-setup-options.ts`, preserving the dependency and pattern-mode seeds; only the companion adds `pluginEnableTiming: 'after-layout-ready'`. Keep `context.desktopAfterLayoutReadyGlobalSetup` explicit in `scripts/vitest-config.ts`: the toolkit cannot infer a companion for a custom setup. The TypeScript toolkit's runner includes `integration-tests:desktop:*` when asked for `integration-tests:desktop`, so the aggregate and desktop commands already run both timings; do not add a second call for the companion. Android retains startup timing, and performance retains its pre-populated setup.

A `data.json` reload replaces the settings object, so an assignment onto it reverts to the file's values mid-suite, silently. Every desktop suite therefore gets the settings component from `scripts/helpers/plugin-settings-component-finder.ts`, passed into the closure through `evalInObsidian`'s `input` (functions there are serialized by source text, so the finder stays self-contained), and both edits and the final restore go through `editAndSave`. Read values through `settingsComponent.settings` each time rather than holding the object. A saved edit outlives the suite in `data.json`, so a suite that changes settings restores them in a `finally`.

## A fresh install follows Obsidian's attachment location, so every test vault seeds pattern mode

Since 13.0.0 `shouldFollowObsidianAttachmentLocation` defaults to on. While it is on, `attachmentFolderPath` is not consulted at all, so an integration vault with no `data.json` of ours quietly turns every pattern suite into a test of Obsidian's own setting. `scripts/helpers/plugin-settings-seed.ts` seeds `{ shouldFollowObsidianAttachmentLocation: false }`. The desktop/Android, demo-vault and performance setups all compose it, and a new project that opens a vault needs it too. The demo vault commits a full `data.json` in pattern mode for the same reason: notes 01 and 08 demonstrate patterns and hard-code `assets/<note>`.

The `@mnaoumov/obsidian-lib` base `loadFromFile` writes the full default record to `data.json` when none exists (since `obsidian-dev-utils` 107.0.0, which it was split from; this plugin used to override it to do so). Without that write, nothing on disk tells a fresh install apart from a user who never saved a setting, and a default change moves both.

## A demo-vault `Try it` promise is asserted by calling the button's helper, not by clicking the button

Every `Try it` button is a one-line call into `demo-vault/_assets/CodeScriptToolkit/demoSetup.ts`, and the helper returns what it did: the files its demo folder holds, the link it wrote, the note it opened. `registerDemoVaultButtonSuite` only proves a button reported success, so `src/demo-vault/demo-vault-try-it.demo-vault.integration.test.ts` calls the SAME helpers through `CodeScript Toolkit`'s `window.requireAsync('/demoSetup.ts')` and asserts the sentence the note wrote about each step. A new `Try it` adds its step there.

- **Each demo owns a folder under `Materials/<NN> <note>/` and resets it.** Its set-up helper deletes and recreates the folder and sets every setting the outcome depends on, because the button suite clicks note `01`'s buttons first and they leave `shouldFollowObsidianAttachmentLocation` on, and the two test files share one vault in either order.
- **A dialog a demo leaves open blocks the collect queue for every later collect.** The shared-attachment dialog has no close button, so the button suite runs with `shouldDismissModals` (it presses `Escape`) and the outcome test dismisses it the same way before it moves on.

## `Only pasted images` is decided by the gesture and the file, never by the sink

An editor paste and an editor drop both end in `ClipboardManager.insertFiles`, and a canvas paste, a canvas drop, a file-explorer drop and a base drop all end in `App.importAttachments` (Obsidian 1.14.4). So reaching one of those methods says nothing about whether the user pasted, and marking every image that reaches `insertFiles` as pasted renamed real files that were dragged in. `src/pasted-images/pasted-image-classifier.ts` decides from four things. Image data with no file path is pasted. A drop is never pasted. A paste of a file counts as pasted, unless `shouldKeepNamesOfPastedNonScreenshotFiles` is on, in which case it counts only when the file is under a minute old or matches `screenshotFilePaths`.

- **That narrowing is OFF by default, and must stay off.** 15.1.0 shipped it as the only behavior, and every capture tool that copies its capture as a file and is not on the default list (issue #97) started keeping its own name. No list can name every capture tool. Keeping the name of a real file the user copies is the narrower need, so it is the opt-in.

- **The gesture is read before the patch's first `await`.** `InsertGestureTrackerComponent` records it from capture-phase `paste` / `drop` listeners and clears it on the next macrotask. Obsidian calls both sinks synchronously inside the DOM event, so a patch that reads `gesture` after an `await` always gets `null`.
- **`importAttachments` is classified only during a paste.** It is also the mobile share sheet's path and every drop target's path, and a share or a drop must keep its name.
- **`src/pasted-images/screenshot-file-paste.desktop.integration.test.ts` dispatches the paste and the drop.** A trusted equivalent would need the user's system clipboard or an OS drag. The file reaches Obsidian with a disk path through the `path` property that `WebUtilsGetPathForFilePatchComponent` reads.

## A new attachment's operation is recorded per `ArrayBuffer`, and picks its folder and name templates

`NewAttachmentOperation` (`src/attachment-saving/new-attachment-operation.ts`) tells a pasted screenshot, a pasted file, a dropped file and anything else (`Other`: another plugin saving through Obsidian, the audio recorder) apart. `PastedImageMarker` records it in `ArrayBufferMap` during the paste or drop, from the same gesture and classification `Only pasted images` uses; `AttachmentSaver` reads it before the JPEG conversion (which replaces the buffer) and hands it to `Substitutions.newAttachmentOperation` for both the name and the folder.

- **Each operation has a folder and a file name template, empty meaning the default** (`PluginSettings.getNewAttachmentFolderPath` / `getNewAttachmentFileName`). A non-empty folder wins over `shouldFollowObsidianAttachmentLocation`, as `collectedAttachmentFolderPath` does. The name template only says HOW: `attachmentRenameMode` still decides WHETHER, so a drop keeps its name under `Only pasted images`.
- **`App.importAttachments` records a drop too, but never as a pasted image** (`record(..., gesture, false)`), so a canvas or file-explorer drop of image data keeps its name as it always did. It now also reads the dropped file's stats, which `createBinary` keeps.
- **Only the saver passes an operation.** The share sheet, the published API, collect and every existing-attachment action leave it `undefined`, so they get the defaults.

## Every operation's templates are one table, `ATTACHMENT_OPERATION_TEMPLATE_KEYS`

`src/settings/attachment-operation.ts` lists the seven operations: the four new-attachment ones, collect, a note rename and the Rename command. It maps each to its persisted keys, which already follow one pattern, `<operation>AttachmentFolderPath` / `<operation>AttachmentFileName`. The note rename and the Rename command have no folder key. Read templates through `PluginSettings.getOperationFileName` / `getOperationFolderPath`, never through the keys one by one. The path manager and the settings tab both do, so a new operation is one table row plus its settings.

- **The keys were never migrated, on purpose.** They already shared one shape, and the settings library binds and validates flat keys only. The `Consistent Attachments and Links` hand-over contract names no template key.
- **The switches stay switches.** `attachmentRenameMode` and `shouldRenameCollectedAttachments` decide WHETHER, and the templates decide HOW. They cannot fold into template values. `shouldRenameCollectedAttachments` also governs `Move attachment to proper folder` and the published `getProperAttachmentPath`, which rename by the generated-name template. `Only pasted images` depends on the gesture classification.
- **The settings UI is one nested page per operation** under `Templates by operation`, built by `getAttachmentOperationPages`. Each entry's `displayValue` reads `Default` or `Custom`, and Obsidian re-evaluates it when the user goes back, so no `update()` call is needed. The declarative API has no collapsible group, so the nested page is the collapse. The defaults stay in `Core` on the main tab.

## `{{originalAttachmentFileName}}` reads a STORE, not the file

Up to 16.0.0 the token read the attachment's current name, so a collect pattern that prepends the note name stacked on every collect. Now `src/original-attachment-names/original-attachment-names-component.ts` keeps a synchronous `path -> arrival name` projection over `obsidian-lib`'s `SharedDataStore`. New devices retain history locally in IndexedDB, scoped by `app.appId`, until explicit sync setup. A pre-existing local replica preserves legacy Markdown synchronization until setup approves JSON; a synced settings file or folder alone never enrolls a new device. Consent, provider choice and attempted relocation exclusions are stored through the public `LocalDataStore` API in the store's own database. New sync setups write JSON, with legacy Markdown read in place. The old `original-attachment-names.json` migrates once per device, with deterministic time-zero observations, and stays untouched as a recovery copy. `{{attachmentFileName}}` is the current name.

- **A device's permanent anchor is chosen once, per device, and never from `data.json`:** `Plugin data` for a replica an earlier version already wrote (local history present the first time this version opens) or a vault already holding `Plugin data/obsidian-custom-attachment-location/original-attachment-names-v1`; otherwise `@Plugin sync data (DO NOT REMOVE)`. It lives in IndexedDB (`original-name-anchor-folder-v1`); a fresh device stays undecided (`''`) and re-checks the vault for the old folder at every load and at enable, and the choice is fixed when sync is first enabled. A different anchor is an independent store, which is why the setting's default can change and the anchor cannot follow it. The initial format is `markdown` everywhere. Explicit setup uses the public `DataStoreLocations` coordinator to announce JSON BEFORE enabling a disabled store, so new setups publish no Markdown history and existing devices do not silently change their sync requirements. `pluginDataFolder` is a proposed destination, applied only by the settings action calling `SharedDataStore.relocate`, never by startup or a settings reload. The library copies and verifies full history, retains readers and the anchor's `locations-v1` discovery records, refuses conflicts and retries incomplete transitions. Keep every listed root synchronized permanently. Disabling sync stops transport and preserves history; it deletes no files. Hidden destinations require explicit permission and externally managed sync; Obsidian Sync cannot carry arbitrary hidden roots. Both setup discovery and later relocation check the device's provider choice. Legacy devices complete setup before relocating. Setup is an honest manual checklist, not a claim that remote devices are ready. Details are in `docs/original-name-storage.md`.
- **The storage page's advice and the Obsidian Sync setup gate come from two modules.** `src/original-attachment-names/obsidian-sync-status.ts` asks the core Sync plugin whether it is enabled, whether `getRemoteVaultId()` is non-empty, and whether its `filter.allowSyncFile(path, false)` would carry a JSON file in each history root. `obsidian-typings` declares neither member yet, so they are read through `Reflect.get` under a `TODO`. `src/original-attachment-names/original-name-sync-advice.ts` turns that and a scan of every string setting for `originalAttachmentFileName` into one advice line. Obsidian enables the core Sync plugin by default, so "on, with no remote vault" (`getRemoteVaultId()` returns `null`) is the common case, and the integration vault has it. Nothing here ever turns synchronization on or off. A device that synchronized under an earlier version keeps doing so, because Git, Syncthing or iCloud may be carrying it unseen, and **Set up external sync** is never gated.
- **A moved anchor is followed, not recreated.** `resolveAnchorFolder` runs at load, at enable and before every flush that has transport on. When the fixed anchor's root is gone, `findAnchorElsewhere` scans `vault.getAllFolders()` for folders ending in `/<plugin id>/<store id>`, sets aside the relocation destinations their `locations-v1` records name, and follows the one candidate left, persisting it as the anchor. An undecided device uses the same search after the legacy and default folders. A candidate whose records start at another folder (any store set up in JSON, since setup records a markdown-to-JSON switch naming the old folder) cannot be opened by `DataStoreLocations`, so the device pauses transport (`blockedMovedAnchorFolder`, a notice, enable refused) instead of forking the history at the old folder, and resumes once the folder is back. Following such a store needs `obsidian-lib` to accept a moved anchor. The unit tests call the mock vault's `reconcile__()` before moving a folder, because folders the store writes through the adapter are not in the mock's tree otherwise.
- **Transport event exclusions come from `containsTransportPath` and `transportRoots`.** Ancestor operations still process known real attachment descendants outside those roots. A manual folder rename remembers mapped metadata roots for that event batch, so its subsequent delete cannot publish a spurious attachment observation. Slash boundaries keep similarly named siblings independent.
- **JSON history is metadata, never an attachment candidate.** `HandedOverSettingsComponent` composes the live store exclusion with the dependency's path predicate without editing that plugin's settings. The callback is lazy because settings load before the store. Collect checks the referenced attachment's path, unused deletion excludes protected folder-scan candidates and preserves an entire attachment unit intersecting history, and existing import/move paths already consult the shared predicate. The storage integration confirms ordinary unused files are deleted while immutable discovery history survives.
- **Relocation tests own their vault.** `integration-tests:storage:desktop` and `integration-tests:storage:android` run the `.storage.integration.test.ts` suite with the standard dependency and pattern-mode seeds. Its retained discovery chain cannot be reset like ordinary settings, so sharing the ordinary projects' vault would redirect later suites' writers. The aggregate and platform integration scripts run these projects sequentially with the ordinary projects.

- **Arrivals and explicit edits have different merge semantics.** The earliest arrival wins; an explicit correction replaces the name. Rename and removal observations carry the arrival identities they saw so delayed duplicate events cannot consume metadata for a replacement file. Events without known metadata retain path semantics so a rename can precede delivery of its arrival record. Folder operations include descendants only, never similarly named siblings.
- **The component owns synchronization and teardown.** It serializes publication, mode changes, relocation and merge, retries pending writes after failure, debounces journal/snapshot/transition `raw` events (excluding acknowledgements), synchronizes every minute and on foregrounding, and flushes before closing IndexedDB on unload. Store files never generate attachment lifecycle observations. Compaction follows each 100 published observations; snapshots retain causal history needed by returning devices. Keep all history locations enabled in the user's sync tool; excluding them from search is a separate Obsidian setting.

- **A new attachment is recorded on its `create`, not when its path is handed out.** `AttachmentPathManager.getAvailablePathForAttachments` calls `expectArrival(path, name)` for every non-rename context, and the store commits it when that path is created within a minute. A dry probe never writes its path, so it records nothing. The saver passes the name the file arrived with explicitly (`originalAttachmentFileName`), since it has already renamed the file by then. The share sheet renames before the resolver sees the file, so its patch remembers each original under the generated name (`getShareImportOriginalFileName`).
- **An existing attachment (collect, move, a note rename) reads the record through `getOriginalAttachmentFileNameParams`.** With no record, `Substitutions` reports the fallback only when a template actually READS the original name. The report remembers the current name and adds the path to one debounced notice per operation. A `ReadApi` read neither records nor warns.
- **Every `AttachmentPathManager` in a unit test needs the store.** `src/attachment-location/attachment-path-manager.test.ts` passes a `strictProxy` with `get`, `expectArrival` and `reportUnknown`, and a handler test that reaches `attachmentPathManager.originalAttachmentNamesComponent` stubs `get`/`set`.

## The store's folders are excluded and explained, by `PluginDataFolderExclusionComponent`

Every existing store folder (`getExistingStoreFolders`: the parent of each transport root that exists) gets `README.md` (`PLUGIN_DATA_FOLDER_README`, rewritten when the text differs) and a `<folder>/` entry in `userIgnoreFilters`; the `pluginDataFolder` setting gets the entry too while this device synchronizes. The entries the plugin added are remembered per device in `app.saveLocalStorage` (`obsidian-custom-attachment-location:managed-ignore-filters-v1`), so a change removes only those: an entry the user already had is never recorded and never removed. Hidden folders get the README but no entry. It reconciles on layout ready, on `loadSettings`, on a `saveSettings` that changes the folder, and on `onStorageChanged` (enable, disable, relocate). The README links to `docs/original-name-storage.md` on `GitHub` until the plugin has a page on mnaoumov.dev.

## A settings sub-page renders outside the tab's container, so scope classes go on the element

Obsidian renders a `SettingDefinitionPage` into its own `.setting-page` beside the plugin tab's `containerEl`, so a `src/styles/main.scss` rule written as a descendant of `.obsidian-custom-attachment-location` never matches anything on a sub-page. 17.2.0's storage-page rules were that shape and none of them applied, which left the description one word wide beside four buttons (#99). Mark the element itself with `addPluginCssClasses(el, '<class>')` and write the rule as a compound `&.<class>` (`original-name-storage-controls`, `default-image-size-dimension-setting-control`). `original-name-sync-advice.desktop.integration.test.ts` measures the storage page's description width, so it fails if the styles stop reaching it.

## Only the original NAME is stored, never the source path

`CopyOriginalAttachmentMetadataComponent` adds one action, **Copy original file name**, to `file-menu`, which Obsidian raises for both file-explorer entries and resolved attachment links. A missing name disables it; the read never calls `reportUnknown` or uses the current name. 17.1.0 also stored and copied the source path; the next release removed it, because it is known only for a desktop drag or an attach from disk, and missing for every paste, every mobile import and every older attachment. `webUtils.getPathForFile` still runs in `FileArrayBufferPatchComponent`, but only to read the file's stats. On load the component deletes the retired `source` / `source-edit` observations 17.1.0 wrote, so they stop syncing, the history ignores any that arrive later, and the legacy JSON migration ignores its `originalPaths` map. Do not bring the path back as a field of a name record.

## The resolver remembers each note's link resolution, and the vault's events forget it

A consumer auditing a vault asks `getAvailablePathForAttachments` once per reference, and each answer numbers the note's attachments for `{{sequenceNumber}}` and `{{cursorLine}}`. `AttachmentPathManager.resolveNoteReferences` therefore keeps each note's resolved references, keyed by the note's path alone, because `getCacheSafe` wraps the cache in a new object on every call. `CustomAttachmentLocationComponent` clears it on every vault `create`, `delete` and `rename` and every metadata `changed`. A stale note is brought up to date inside `getCacheSafe`, whose recompute raises `changed` before the walk reads the memo. Only the resolution is remembered: the `isNoteEx` filtering and the numbering run on every call, because they read settings that raise neither event. `attachment-path-audit-burst.desktop-performance.integration.test.ts` counts `getFirstLinkpathDest` calls to hold this to one walk per burst.

A resolver call that skips both the duplicate check and the folder creation is a query. It claims no self-write path, expects no arrival and prepares no inserted link text, because nothing will be written at the path it returns.

## Bulk commands are wrapped in git commits from OUTSIDE the operation queue

The collect, delete-unused, move-to-proper-folder and prune commands run their work inside `BulkOperationCommitComponent.runBulkOperation` (`@mnaoumov/obsidian-lib`), which records each run as `chore: before OP<n>` plus `OP<n>: <summary>` when `shouldCommitBulkOperations` is on, the app is desktop and the vault is in a `git` work tree. The summary is English on purpose (`src/bulk-operations/bulk-operation-summary.ts`): it is a commit subject.

- **Wrap at the command, never inside a queued operation.** The component's settle step calls `flushQueue()`, so a wrap inside an `addToQueue` operation would wait on itself. That is why `collectAttachmentsEntireVault`, `deleteUnusedAttachmentsEntireVault` and `deleteUnusedAttachmentsInAbstractFiles` await the queue (`addToQueueAndWait`), and the file and folder collect commands call `collectAttachmentsInAbstractFilesAndWait`. The automatic collect and the published API are not user-triggered bulk commands and stay unwrapped.
- **Prune flushes the original-name store inside the operation.** The store writes its Markdown files on a debounce, so without `flush()` the run's commit would hold nothing.
- **The heartbeat comes from `loop()`.** Every wrapped command except prune iterates through `loop()`, which reports progress to the lease lock since `obsidian-lib` 10.4.0. A dialog the run opens and leaves waiting, such as the delete confirmation, reports none, so after two minutes the lock reads as stale.
- **`src/bulk-operations/bulk-operation-commit.desktop.integration.test.ts` runs `git` asynchronously, and turns `core.autocrlf` off in its repository.** A blocking `execFileSync` stalls the renderer while `git` rewrites `.git`, and on Windows Obsidian's watcher then drops the events for the files a revert puts back, so the vault never sees them. The machine's `core.autocrlf` rewrites the note's line endings on the revert's checkout. Read an `OP<n>` commit's files with `--no-renames`: `git` otherwise reports the move's copy and delete as one rename.

## `Rename attachments in current note` renames in place, and its empty template is the generated one

`src/rename-attachments/rename-attachments-in-file-command-handler.ts` renames each attachment a Markdown note links, through `AttachmentPathManager.getRenamedAttachmentPath` under `ActionContext.RenameAttachments`. It never changes a folder: that is collecting's job, and an attachment kept in a shared folder on purpose stays there. A template's subfolder part is dropped, a taken name gets the duplicate suffix, and an attachment parked under that suffix beside its taken name stays put, so a rerun converges.

- **`manuallyRenamedAttachmentFileName` empty means `generatedAttachmentFileName`**, unlike the collect and note-rename templates, whose empty value keeps the name. Keeping the name would make the command do nothing by default.
- **It skips four kinds**, each counted in the closing notice and named in the console: a path the handler ignores, a file inside an attachment unit folder, a sidecar with a base (`findSidecarBase`; the base's rename carries it), and an attachment another note links too (notes the multiple-notes check excludes do not count).
- **Canvas is out**: its text-node embeds are not in the metadata cache, so `renameSafe` would leave them on the old name.
- It is wrapped in `runBulkOperation` from outside `addToQueueAndWait`, like the other bulk commands.
